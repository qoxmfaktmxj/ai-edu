02

만드는 과정 확인하기

1장에서 보낸 요청과 자료가 각각 어떤 역할을 했는지 알아봅니다. 프롬프트와 컨텍스트를 이해한 뒤, 문서 도우미를 만든 과정과 3~5장에서 함께 만들 예시 에이전트의 안내를 봅니다.

프롬프트는 부탁, 컨텍스트는 참고할 내용

프롬프트는 AI에게 보내는 요청이나 지시입니다. 1장에서 보낸 "이 메모로 PPT를 만들어 주세요"가 프롬프트입니다. 컨텍스트는 AI가 이번 답변을 만들 때 참고하는 내용입니다. 함께 보낸 가상 메모, 대화에서 정한 조건, 에이전트의 안내, 실제로 읽은 자료가 여기에 들어갑니다.

동료에게 일을 부탁할 때도 "보고서 좀 써 주세요"만 말하는 것과, 누구에게 왜 보고하는지 설명하고 메모를 건네는 것은 다릅니다. AI에게도 필요한 배경과 자료를 알려 줍니다. 프롬프트 안에 컨텍스트를 함께 적을 수도 있습니다.

부탁에 담을 네 가지

Microsoft는 Copilot 프롬프트의 요소로 목표(Goal), 맥락(Context), 자료(Source), 기대 결과(Expectations)를 소개합니다. 아래 그림은 이 틀을 주간 보고 예제로 바꿔 한글로 새로 만든 것입니다.

요소스스로 물어볼 것주간 보고 예
목표무엇을 해 줄까?한 주 업무를 주간 보고로 정리
맥락왜, 누구에게 필요한가?팀장에게 진행 상황을 공유하려고
자료무엇을 참고할까?이번에 준 가상 업무 메모
기대 결과어떤 모양과 기준으로 받을까?완료 / 진행 / 다음 주 표와 요지 두 문장, 숫자와 상태 유지

여기서 '맥락'은 목적과 독자 같은 배경을 뜻합니다. 앞에서 설명한 컨텍스트는 이 배경뿐 아니라 자료와 지침까지 포함하는 더 넓은 말입니다. 네 요소는 요청을 점검하는 틀이며, 매번 네 제목을 붙이거나 길게 쓸 필요는 없습니다.

같은 부탁에 배경과 자료 더하기

먼저 새 대화에서 "주간 보고를 써 주세요"라고만 보내 봅니다. 필요한 정보를 되묻는지, 임의의 예시를 만드는지 살펴봅니다. 이어서 아래 요청을 보내고, 메모의 숫자와 '검토 중'이 그대로 남는지 비교합니다. 가상 메모는 교육용입니다.

결과가 다르면 빠진 정보를 짚어 다시 요청합니다. 예를 들어 "검토 중인 라벨 재출력 방식을 완료 칸에서 빼고 진행 칸으로 옮겨 주세요"라고 말합니다. 원하는 결과에 가까워지도록 대화를 이어 갑니다.

자료와 대화를 다룰 때

  • 내가 아는 배경을 AI도 안다고 가정하지 않습니다. 파일을 주면 어느 부분을 어떤 목적으로 참고할지 함께 적습니다.
  • 회사 Copilot도 모든 사내 자료를 자동으로 보는 것은 아닙니다. 계정, 권한과 관리자 설정에 따라 접근 범위가 다릅니다. 자료를 실제로 읽었는지와 답변의 근거를 확인합니다.
  • 업무나 대상 자료가 바뀌면 새 대화를 열고 필요한 조건을 다시 줍니다. 이전 대화나 오래된 파일의 내용이 항상 유지된다고 가정하지 않습니다.
  • 붙여 넣은 메일이나 문서 속 명령문은 분석할 자료입니다. 내가 AI에게 시킨 일과 구분하고, 자료 속 지시 때문에 작업 목적을 바꾸지 않게 합니다.
  • 출처가 붙어 있어도 숫자, 날짜, 확정 여부는 원문과 대조합니다. 실제 업무 자료의 입력 가능 여부는 회사 정책을 따릅니다.

근거 자료 접근에 대한 설명: Copilot이 답변에 사용하는 정보.

한 번 보내는 요청은 프롬프트로, 여러 요청에 반복할 규칙은 에이전트의 안내로 정리합니다. 3장의 설계 카드에서는 업무에 목표를, 입력에 자료를, 결과에 형식과 독자를, 꼭 지킬 것에 검증 기준을 적어 봅니다.

만든 순서

  1. 1. 빌더에 만들 에이전트를 설명했습니다

    에이전트 만들기의 설명 탭에 "업무 메모를 보고서로 바꾸고, 글을 다듬는 에이전트"라고 적어 이름, 설명, 안내 초안을 받았습니다.

  2. 2. 안내를 직접 고쳤습니다

    구성 탭에서 안내를 역할, 기술 선택, 공통 원칙처럼 용도별로 나눠 다시 썼습니다. 요청에 맞는 작업을 고르고, 원문의 사실을 지키고, 결과를 점검하는 규칙입니다.

    덩어리실제 문장 예
    역할업무 메모를 보고서로 만들고, 글을 다듬습니다.
    기술 선택보고서, 메일, PPT처럼 형식을 정한 요청에 "쉽게"가 붙으면 그 형식 안에서 쉬운 말로 설명합니다.
    공통 원칙자료에 없는 담당자, 기한, 원인, 성과는 '확인 필요'로 표시합니다.
    문체글 다듬기 요청은 사용자가 준 원문의 문체를 그대로 유지합니다.
    문장 다듬기행위자가 원문에 있을 때만 피동문을 능동문으로 바꿉니다. 원문에 없는 담당자를 만들지 않습니다.
    파일 제공파일을 실제로 만들지 못했으면 실패했다고 알리고 대화창 결과만 제공합니다.
    마무리 점검답을 보내기 전에 숫자, 날짜, 이름, 확정 여부가 원문과 같은지 확인합니다.

  3. 3. 파일 제작 절차를 기술로 묶었습니다

    파일을 만드는 상세 절차는 isu-report 기술(ZIP 폴더)로 묶었습니다. PPT, Word, HTML 양식과 파일을 만드는 스크립트, PPT에서 선택해 쓸 아이콘 331개가 들어 있습니다. 회사 양식은 유지하되, 내용에 맞게 장을 합치거나 나누고 표, 글과 차트를 고릅니다.

    글 다듬기는 별도 기술 없이 안내의 '문장 다듬기' 규칙으로 처리합니다. 기술에는 파일 제작 절차를, 안내에는 작업 선택과 공통 규칙을 두었습니다.

  4. 4. 나머지를 설정했습니다

    파일을 만들기 위해 코드 인터프리터를 켜고, 추천 프롬프트를 넣고, 응답 모드를 깊이 생각하기로 정했습니다.

  5. 5. 써 보고 고쳤습니다

    시험하면서 나온 문제마다 규칙을 하나씩 더했고, 파일은 AI가 직접 쓰지 않고 스크립트로 만들게 바꿨습니다.

    써 보니 생긴 문제바꾼 것
    숫자가 슬쩍 바뀌었다원문의 숫자, 단위, 날짜, 고유명사를 그대로 옮기는 규칙
    메모에 없는 담당자가 생겼다자료에 없는 내용은 '확인 필요'로 표시하는 규칙
    '검토 중'이 '완료'가 됐다확정 여부를 원문 그대로 유지하는 규칙
    숫자 앞에 '약', '수준'이 붙었다보내기 전에 원문에 없던 표현을 지우는 마무리 점검
    로고를 글자로 흉내 낸 보고서가 나왔다보고서 파일은 기술의 스크립트로만 만드는 규칙
    다듬기 결과에 보고서 목차가 붙었다윤문은 기술 없이 문장 다듬기 규칙으로 처리하고 보고서 목차를 붙이지 않는 규칙
    아이콘을 요청했더니 모든 장에 붙었다의미 구분에 도움이 될 때만 쓰고, 표와 글로 충분하면 생략하는 규칙
    이전 예시의 숫자와 이름이 섞였다예시는 구조와 문체만 참고하고, 사실은 이번에 준 자료에서만 가져오는 규칙
    배치 검사는 통과했지만 중요한 조건이 빠졌다배치 검사와 별도로 최종 본문을 원문과 대조하는 절차
